# Принятые проектные решения (DECISIONS.md)

## Решение 1: Отказ от публичного setter в пользу доменных методов
**Проблема:** Публичный `setStatus(TripStatus)` позволяет внешнему коду устанавливать любое состояние, игнорируя бизнес-правила переходов. Это приводит к нарушению целостности жизненного цикла (например, переход из DRAFT сразу в COMPLETED).
**Решение:** Сеттер удалён. Вместо него реализованы доменные методы `submit()`, `approve()`, `reject()`, `cancel()`, `complete()`, каждый из которых проверяет текущее состояние и разрешает только валидные переходы.
**Обоснование:** Это реализует принцип инкапсуляции состояния. Объект сам управляет своим жизненным циклом, внешний код не может "сломать" бизнес-правила. Недопустимые переходы вызывают `IllegalStateException` с понятным сообщением.

## Решение 2: Проверка минимальной длины причины отклонения
**Проблема:** Без минимальной длины причины отклонения пользователи могут вводить формальные комментарии ("нет", "не ок"), что делает аудит бессмысленным.
**Решение:** В методе `reject(String reason)` добавлена проверка `reason.trim().length() >= MIN_REJECTION_REASON_LENGTH` (вариант 7: 40 символов). Значение вынесено в константу.
**Обоснование:** Это гарантирует содержательность комментариев при отклонении. Вынесение порога в константу позволяет легко изменить требование (например, до 50 символов) без поиска "магических чисел" по коду.
